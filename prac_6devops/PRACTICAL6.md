## 4. Етапи розробки та Git Flow
Робота велася за адаптованою моделлю гілкування. Головним правилом команди була заборона прямого пушу в гілку `main`.

1. [cite_start]**Розподіл завдань:** Кожен учасник створював ізольовану гілку (`git branch`) під свою конкретну задачу (наприклад, `feature/bot-api`, `feature/database-setup`)[cite: 482, 483].
2. [cite_start]**Локальна розробка:** Робота велася паралельно з використанням стандартних команд `git commit` та `git push` для збереження змін у своїх віддалених гілках[cite: 480].
3. **Об'єднання та вирішення конфліктів:** Інтеграція коду відбувалася через механізм Pull Requests. Під час злиття (`git merge`) гілки з оновленою базою даних та гілки з API виник конфлікт у головному файлі `app.py`. [cite_start]Команда успішно розв'язала його шляхом спільного обговорення та ручного редагування конфліктних блоків безпосередньо перед фінальним комітом злиття[cite: 484, 485].

[cite_start]**Головні висновки[cite: 491]:**
* Регулярне підтягування змін (`git pull`) з основної гілки дозволяє мінімізувати кількість merge-конфліктів.
* Чіткий розподіл завдань у Trello запобігає дублюванню роботи.
* Інструментарій Git є абсолютно незамінним для спільної розробки, оскільки він дозволяє безпечно інтегрувати код від різних учасників і зберігає повну історію змін.
